# Monorepo (pnpm + Turborepo)

pnpm workspaces + Turborepo across `apps/`, `packages/`, and `examples/`. This file covers the mechanics of the workspace itself — how packages depend on each other, how Turborepo orders/caches tasks, and how packages expose their public surface — as background for working in any single app/package.

## Workspace layout and internal dependencies

`pnpm-workspace.yaml` includes every top-level `apps/*`, `packages/*`, `examples/*` directory as a workspace member:

```yaml
packages:
  - 'apps/*'
  - 'packages/*'
  - 'examples/*'
```

Internal cross-package dependencies always use the `workspace:*` protocol, never a version range or `file:`/`link:` path, e.g. `packages/jwt/package.json`:

```json
"dependencies": { "@repo/auth": "workspace:*" },
"devDependencies": { "@repo/eslint-config": "workspace:*", "@repo/typescript-config": "workspace:*" }
```

pnpm resolves `workspace:*` to the local package via symlinks regardless of its `version` field (every internal package is pinned at `"version": "0.0.0"` and never bumped — versioning doesn't matter because nothing here is published). All internal packages are named `@repo/<name>` and are `"private": true`.

Native/build-step dependencies that need `postinstall`/build scripts approved are listed once, at the root, in `package.json`'s `pnpm.onlyBuiltDependencies` array (`@nestjs/core`, `@prisma/client`, `@prisma/engines`, `bcrypt`, `sharp`, `esbuild`, etc.) — pnpm otherwise blocks arbitrary install scripts by default. Add a new dependency here if `pnpm install` warns about a blocked build script, rather than working around it per-package.

## Turborepo task graph: `dependsOn: ["^build"]` and per-package output overrides

`turbo.json`'s default `build` task declares `"dependsOn": ["^build"]` — the `^` means "the `build` task of every package this package depends on must finish first." This is what makes `pnpm build` a topological build: `@repo/nestjs` (an app) depends on `@repo/contract`, which depends on `@repo/virtual-authenticator`, so `pnpm build` builds leaf packages first and the app last, without anyone having to sequence it by hand. `lint` and `check-types` use the same `^`-prefixed pattern so a package is only linted/type-checked after its dependencies' outputs (generated files) exist.

Most packages just inherit the default `build` task (`outputs: ["dist/**", "generated/**", "build/**"]`), but several get a **named override** — `"@repo/<name>#build"` — because their real build output doesn't match that default and Turborepo needs to know exactly what to cache/hash:

```json
"@repo/prisma#build": {
  "dependsOn": ["^build"],
  "outputs": ["src/generated/client/**"]
},
"@repo/keys#build": {
  "dependsOn": ["^build"],
  "outputs": ["src/validation/index.ts"]
},
"@repo/console#build": {
  "dependsOn": ["^build"],
  "outputs": [".next/**", "public/generated/**"]
}
```

- `@repo/prisma#build` runs `prisma generate`, which writes the generated Prisma Client into `src/generated/client/` (not `dist/`) — see `packages/prisma/package.json`'s `"build": "prisma generate"`.
- `@repo/keys#build` and `@repo/virtual-authenticator#build` don't compile anything; their `build` script is `run-p barrel:*`, which runs `../../scripts/barrel.ts` to regenerate barrel `index.ts` files for directories like `src/validation` and `src/dto` (auto re-exporting every sibling file). The output path is the generated barrel file itself, e.g. `packages/virtual-authenticator/package.json`: `"barrel:validation": "../../scripts/barrel.ts ./src/validation"`.
- `@repo/console#build` is a Next.js app (`next build --turbopack`), so its real output is `.next/**` plus `public/generated/**` (a generated OpenAPI/client artifact copied into the app's public dir at build time), not `dist/**`.
- `@repo/virtual-authenticator-agent#build` and `@repo/types#build` follow the same reasoning — list exactly the generated file(s) a package's non-standard build step produces (`src/dom.ts` for `@repo/types`, generated by `./scripts/extract-dom-types.ts`) so Turborepo's cache is neither too narrow (missing an output, causing stale artifacts on cache hit) nor too broad (caching `dist/**` on a package that never writes there).

When adding a package whose build step doesn't produce plain `dist/**`, add a `"@repo/<name>#build"` override rather than letting it silently rely on the default `outputs` glob.

Tasks with no meaningful caching or that must stay attached to a terminal are marked accordingly: `dev`/`start` set `"cache": false, "persistent": true`. `format`/`format:check` have no config (they run, uncached, with no dependency ordering). Note `test`/`test:unit`/`test:integration` are **not** Turborepo tasks at all — the root `package.json` scripts (`"test": "vitest run --config vitest.config.ts"`) invoke Vitest directly across its own `projects` glob (see [.docs/vitest.md](./vitest.md)) instead of going through `turbo run test`.

## Scoping commands to one package

Both orders work; both are used in this repo (see [AGENTS.md](../AGENTS.md#commands) and [README.md](../README.md)):

```bash
pnpm build --filter @repo/nestjs          # filter after the script
pnpm --filter '@repo/prisma' db:migrate   # filter before the script
pnpm --filter @repo/nextjs-example db:generate
pnpm dev --filter '!@repo/nextjs-example' --filter '!@repo/wxt'   # negation, e.g. to exclude slow/optional apps from dev
```

`db:migrate`, `db:studio`, etc. only exist on `@repo/prisma`'s `package.json`, so they must be filtered — running them at the root would fail (no matching script) or (worse, for scripts that do exist at the root under a different meaning) run the wrong thing. Prefer filtering to a specific package over `cd`-ing into its directory, since filtered commands still resolve workspace symlinks and run from the repo root's pnpm context.

## Shared config packages: extend, don't duplicate

Four packages exist purely to be imported by other packages' config files, never to ship runtime code:

- **`packages/typescript-config`** — base `tsconfig.json`s (`base.json`, `nestjs.json`, `nextjs.json`, `react-library.json`, `plasmo.json`). A package's own `tsconfig.json` is almost always just:
  ```json
  { "extends": "@repo/typescript-config/base.json", "include": ["src"], "exclude": ["node_modules"] }
  ```
- **`packages/eslint-config`** — `base.js`/`nestjs.js`/`nextjs.js`, each exporting a flat ESLint config array built on `typescript-eslint` + `eslint-config-prettier` + the `turbo` plugin. A package's `eslint.config.mjs` is typically just `import { config } from '@repo/eslint-config/base'; export default config;`.
- **`packages/rollup-config`** — `createRollupConfig()` (`packages/rollup-config/src/createRollupConfig.ts`) builds a full Rollup config (SWC transpile, externalize `@repo/*` deps as bundled rather than external, tsconfig path resolution, watch-mode `run` plugin). Apps that need a Node bundle (`apps/auth-server`, `apps/api-bff`) have a one-line `rollup.config.js`: `export default createRollupConfig({ input: 'src/index.ts' });`.
- **`packages/vitest-config`** — see [.docs/vitest.md](./vitest.md).

The pattern is the same in all four: write the shared logic once as a small package with its own `exports` map, then every consumer's local config file is a 1-5 line file that imports and (optionally) merges in package-specific overrides. Don't copy a `tsconfig.json`/`eslint.config.mjs`/rollup or vitest config from one package into a new one and hand-edit it — extend the shared package instead, the same way the existing packages do.

## `exports` maps: subpath exports instead of one default export

Every internal package's `package.json` uses an `exports` map with multiple named subpaths rather than a single `"."` entry re-exporting everything. This keeps import paths self-documenting and lets a package deliberately not expose internals (e.g. no `"."` entry at all, only specific subpaths). Two real examples:

```json
// packages/contract/package.json
"exports": {
  "./nestjs": "./src/nestjs/index.ts",
  "./auth-server": "./src/auth-server/index.ts",
  "./validation": "./src/validation/index.ts",
  "./dto": "./src/dto/index.ts"
}
```

```json
// packages/auth/package.json
"exports": {
  ".": "./src/index.ts",
  "./enums": "./src/enums/index.ts",
  "./validation": "./src/validation/index.ts",
  "./helpers": "./src/helpers/index.ts"
}
```

Consumers import exactly the slice they need: `apps/nestjs/src/controllers/VirtualAuthenticators.controller.ts` does `import { Permission } from '@repo/auth/enums'` and `import { ... } from '@repo/contract/dto'` plus `import { nestjsContract } from '@repo/contract/nestjs'` — never a blanket `import * as contract from '@repo/contract'`. Exports point straight at TypeScript source (`./src/...index.ts`), not at a `dist/` build output, since internal packages are consumed as workspace source and only bundled at the app boundary (see `createRollupConfig`'s `externals({ exclude: [/@repo\/.*/] })`, which tells Rollup to bundle `@repo/*` source rather than treat it as an external dependency).

Some packages also export their test fakes as a subpath so other packages can reuse them instead of re-implementing: `packages/keys/package.json` and `packages/jwt/package.json` both include `"./__tests__/helpers": "./__tests__/helpers/index.ts"`.

When adding a new module to a package (a new enum file, a new validation schema group), add a matching subpath to `exports` rather than dumping everything through the package's root `"."` export or reaching into another package's `src/` with a deep relative import.
